## What is known vs still open

- Native benchmark separates fresh device-side hierarchy dumping, XML transfer, local read/node counting, foreground queries and streamed screenshots. Local scan is **not** the complete pi-droid XML parser.
- Tool tracing does **not** currently attribute internal cache behavior, OCR, reconnect, subprocesses, fallback or page-load waits. The variable slow UI dumps need those spans before assigning a cause.
- Unobserved trace time includes model work, user pauses, other tools and orchestration. It is not a measurement of LLM latency.
- Streamed screenshot timing is a different implementation from pi-droid's capture-to-device-file/pull path; a direct comparison has not been run.
- No controlled keyboard-backend, persistent UI server, Accessibility, browser DOM/CDP, USB-vs-Wi-Fi, OCR/vision or Rust comparison has been completed. No alternative has been proved best or ruled out.
- The successful second connection does not establish that wireless stability is fixed.

## Next work, in order

1. **Define a red-capable, bounded feedback loop.** Use a stable fixture/app or repeatable browser page, with target text/field assertions and explicit capture/time budgets. Separate backend benchmarks from the real shopping workflow, whose page content and network change. Record correctness and failures alongside latency; enough repeated samples for useful tail observations, not population claims from three rounds.
2. **Instrument real pi-droid stages, without retaining content.** Inspect `exec.ts`, `ui-tree.ts`, `screenshot.ts`, `cache.ts`, `ocr.ts`, `reconnect.ts` and `annotate.ts`. Distinguish command duration, capture, transfer, parse, foreground lookup, cache, OCR fallback and reconnect. Carry explicit error/timeout metadata rather than guessing from elapsed time. Cancellation should bound the whole observation, not leave sibling work running after a parallel failure.
3. **Reduce observations and model round trips safely.** Small action/wait/observe batches through codemode or a guarded compound tool; focused output rather than all footer/review elements; an information-reading mode that includes non-interactive text; a text-only observation path that does not capture an unused screenshot. Retain verification checkpoints. Do not blindly increase cache TTL or reuse stale coordinates.
4. **Prototype perception alternatives behind one seam.** Baseline CLI UIAutomator; persistent UIAutomator/instrumentation or Accessibility backend; browser DOM/CDP if this Brave/device setup actually supports it. Check feasibility first. Compare setup, permissions, correctness, median/tail latency, fallback behavior and maintenance. Browser DOM success is not a native-app replacement.
5. **Evaluate input as a lifecycle.** Focus, set/replace text, verify accessible field value, restore original IME. Compare ADBKeyboard, simple `input text`, Accessibility `ACTION_SET_TEXT`, and browser DOM input in their supported domains. Review broadcast exposure before sensitive input. Reconcile preflight component recognition with the new guard. Never report broadcast completion as verified insertion.
6. **Optimize transport or language only if justified.** Persistent helpers or fewer shell calls may help. A TypeScript-to-Rust rewrite alone does not eliminate waits inside Android's UI dump. A Rust helper can be a candidate backend, not a presumed win.

For each change: one hypothesis, one controlled variable, before/after evidence, regression coverage at the real seam, and explicit remaining limits. Do not call the entire system fixed after unit tests pass.
